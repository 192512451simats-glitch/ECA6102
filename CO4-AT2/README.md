**Project Overview and Objectives**

The main objective of this lab assignment is to understand how digital forensics work during a cyber incident investigation. In this project I have demonstrated the step by step workflow of acquiring evidence from a target machine preserving its integrity using hashing techniques analyzing the collected evidence using standard forensic tools and creating an incident investigation report. The primary goal is to collect evidence without making any changes to original disk data and to identify suspicious files or network connections using both disk and memory forensics.

**Tools Used**

For completing this digital forensics investigation I used FTK Imager software to create raw disk images in.dd format and to capture memory RAM dumps from the target machine. For analyzing the acquired hard drive image and extracting registry artifacts I used the source Autopsy tool. Volatility Framework command line tool was used to analyze system RAM dumps and inspect running processes or active network sockets. HashMyFiles and standard terminal commands like sha256sum and md5sum were used to calculate and re-verify hash values to ensure evidence preservation.

**Implementation Procedure**
**Evidence Acquisition Phase**

In the acquisition phase I started by running FTK Imager tool as Administrator on the target Windows system. I clicked on Create Disk Image option. Selected the physical target hard drive to clone. I selected the output image format as RAW (.dd) to maintain forensic compatibility. The destination folder was set to./evidence/. Named the output file as disk_image.dd. Next I clicked on Capture Memory option in FTK Imager to dump volatile system RAM into a file named ram_dump.raw before shutting down or disturbing the target machine.

**Evidence Preservation Phase**

To preserve the evidence integrity and maintain chain of custody I recorded the MD5 and SHA-256 hash values generated by FTK Imager after acquisition. Then I opened Linux terminal. Ran command sha256sum./evidence/disk_image.dd > original_hash.txt and md5sum./evidence/ram_dump.raw >> original_hash.txt to verify that hashes matched perfectly with original values. I copied the image files into an external storage drive mounted with write-block protection so that no accidental write modification occurs during analysis.

**Forensic Analysis Phase**

During disk analysis using Autopsy tool I created a case named Case_01 and added disk_image.dd as main data source. I ran modules like Keyword Search, Recent Activity and File Type Identification. Autopsy flagged an executable named update_service.exe located inside C:\Users\Public\Downloads\ path. I also extracted registry hive NTUSER.DAT. Analyzed UserAssist keys to confirm the file execution history on victim system.

For memory analysis using Volatility framework I first checked RAM profile using command volatility -f imageinfo. Then I listed all running processes using volatility -f ram_dump.raw --profile=Win7SP1x64 pslist and identified a suspicious process named malware_spawn.exe running under process ID 2484. To check network activity I executed volatility -f ram_dump.raw --profile=Win7SP1x64 command which showed an active outbound connection from process ID 2484 to external C2 server IP address 192.168.1.105 on port 4444.

**Evidence Integrity Verification Data**

The generated disk image file disk_image.dd produced MD5 hash value 4a8f9c12b7e51084d89a1c2234e5f61a and SHA-256 hash value a3b890f12cde451198e7bb664210ab23, which remained completely matched after verification. The memory dump file ram_dump.raw produced MD5 hash value 8901ab245ef789c0123456789abcdef0 and SHA-256 hash value 11223344556677889900aabbccddeeff. The chain of custody item ID E-101 was assigned to 500GB target disk image collected by Student Investigator on 25-08-2026 at 10:30 AM in Computer Security Lab.

**Investigation Findings and Results**

From the forensic analysis I found that the target machine was compromised by a reverse shell malware. The suspicious file update_service.exe was dropped into user downloads directory. The registry logs proved that the file was executed manually which spawned process ID 2484 in RAM memory. The volatile memory scan confirmed that this process established a backdoor connection to external attacker IP 192.168.1.105, over port 4444 allowing unauthorized remote command execution and data exfiltration.
